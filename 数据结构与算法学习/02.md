<details>
<summary>第 1 题 · 为什么要做复杂度分析</summary>

> 两者不矛盾，是"宏观选型"与"微观验证"的关系：
> - 性能测试是**事后统计**，依赖具体机器、具体数据。A 机器上快的代码换个环境可能变慢，小规模数据测出来的结论推不到大规模。
> - 复杂度分析看的是**增长趋势**，不依赖环境和测试数据。写代码之前就能判断"数据规模涨 10 倍，耗时会涨 10 倍还是 100 倍"，提前排除明显低效的方案。
> - 复杂度分析成本极低——只要看代码结构（有没有嵌套循环、是乘还是除），几秒钟就能估出来；性能测试要搭环境、造数据、跑基准。
> - 所以不是"多此一举"：**复杂度分析用来做设计决策，性能测试用来验证具体实现**。先用前者圈定方向，再用后者确认落地效果。

</details>

<details>
<summary>第 2 题 · 三段代码的复杂度</summary>

> **(a)** `O(n*m)`。两层循环的规模是 n 和 m 两个独立变量，不能偷懒写成 O(n²)。这正是 01 篇提到的"两个数据规模"情形——加法法则在这里不合并，写成 O(n+m) 或 O(n·m) 要按实际结构判断；此处是嵌套（乘法），所以是 O(n·m)。
>
> **(b)** `O(logn)`。i 每次乘 3，走的是 3⁰, 3¹, 3²… 约 log₃n 次。由于换底公式 `log₃n = log₃2 × log₂n`，系数 log₃2 是常数，大 O 忽略，统一写 O(logn)。
>
> **(c)** `O(n)`——这是最容易错的一题。很多同学看到"循环里调用函数"就套乘法法则写成 O(n²)，但注意 `g(100)` 传进去的是**常数 100**，g 内部 `sum(range(100))` 执行固定 100 次，是 O(1)。所以外层 n 次 × 内层 O(1) = O(n)。**判断是否相乘，要看被调函数的复杂度是否随 n 增长。**

</details>

<details>
<summary>第 3 题 · 小规模时 O(n²) 更快，复杂度分析没意义？</summary>

> 这个说法对一半，错一半。
> - **对的部分**：n 很小时，常数因子和低阶项主导，O(n²) 算法若常数极小，确实可能比 O(nlogn) 快。工程里小规模数据用插入排序而不是快排，就是这个道理。
> - **错的部分**：复杂度分析从来不承诺"任何规模下都更快"，它承诺的是**规模增大后的增长趋势**。n 从 100 涨到 100000 时，O(nlogn) 必然反超并拉开差距。
> - 所以正确态度是：**用复杂度分析判断"规模上去了谁赢"，用具体测试判断"当前规模下谁赢"**。两者结合，而不是二选一。复杂度分析不是没意义，而是给了你一个脱离具体环境的长期视角。

</details>

## 正文内容

### 一、先想一个问题：数组为什么从 0 开始编号？

几乎每一门编程语言的数组（Python 的 list、C 的数组、Java 的 array）都是从 0 开始。你有没有想过：**为什么不从 1 开始，更符合人的直觉？**

**先自己想 15 秒**，再往下看。

……

这个问题背后藏着数组最核心的特性——**连续存储**。理解了它，数组的优点和缺点会一次性全部串起来。

### 二、数组的本质：一整块连续的内存

把内存想象成一排格子。数组就是**向系统申请一整段连续的格子**，每个格子里放一个元素，大小相同、紧挨着。

```
内存地址:  1000   1004   1008   1012   1016
           ┌─────┬─────┬─────┬─────┬─────┐
           │  a0 │  a1 │  a2 │  a3 │  a4 │
           └─────┴─────┴─────┴─────┴─────┘
下标:         0     1     2     3     4
```

（假设每个元素占 4 字节）

**连续**带来一个巨大的好处：**按下标找元素不需要从头数，直接算地址**。

```
元素地址 = 首地址 + 下标 × 单个元素大小
```

比如要找 `a[3]`：`1000 + 3 × 4 = 1012`，一步到位。

这就是为什么数组的**随机访问是 O(1)**——不管数组有 10 个元素还是 1000 万个元素，取 `a[k]` 都只要一次算术运算。用 01 篇的口诀看：没有任何循环，执行次数不随 n 增长，所以是 O(1)。

> 类比：连续存储像一排连号座位，你拿着票号"12 排 8 座"直接走过去；链表像演唱会现场随便站的人，你得从头一个个问"你是几号"。

### 三、回到那个问题：为什么从 0 开始？

现在答案清楚了。对比两种编号方式：

- **从 0 开始**：`a[k]` 的地址 = `首地址 + k × 元素大小`，一步算出。
- **从 1 开始**：`a[k]` 的地址 = `首地址 + (k - 1) × 元素大小`，每次寻址**多一次减法**。

数组是最底层的操作，每一次访问都会做这个计算。省掉的那一次减法，在海量访问下会被放大成可观的性能差异。所以早期语言（C）选择了从 0 开始，后面绝大多数语言沿袭了这个习惯。

> 记住这个思路：**很多"看起来奇怪"的设计，本质上是把开销从高频路径上挪走**。以后你看到类似设计（比如位运算、内存对齐），都可以往这个方向想。

### 四、连续性的代价：插入和删除是 O(n)

天下没有免费的午餐。为了保持"连续"，数组在插入/删除时必须**搬移元素**。

**头部插入**一个元素：

```
插入前:  [ a,  b,  c,  d ]
插入 X:  [ X,  a,  b,  c,  d ]   ← 原来 4 个元素全部后移一位
```

需要移动 n 个元素。用 01 篇的口诀：一个循环跑 n 次 → **O(n)**。

**尾部插入**则不用搬移任何元素 → **O(1)**（暂不考虑扩容）。

**删除中间**某个元素：后面的元素要全部前移填补空缺 → 也是 **O(n)**。

这就是数组的双刃剑：

| 操作 | 复杂度 | 原因 |
|---|---|---|
| 按下标访问 `a[k]` | O(1) | 直接算地址，不循环 |
| 尾部插入 | O(1) | 无需搬移（不考虑扩容） |
| 头部/中间插入 | O(n) | 要搬移后续元素 |
| 删除任意元素 | O(n) | 要搬移后续元素 |

### 五、两个实用技巧（面试常考）

**技巧 1：不要求有序时，删除可以 O(1)。**

如果数组只是"装一堆元素"，不要求保持顺序，删除下标 k 的元素时，可以**把最后一个元素拿过来填到 k 的位置**，然后数组长度减 1：

```python
def remove_unordered(arr, k):
    arr[k] = arr[-1]   # 用末尾元素顶替，一步完成
    arr.pop()          # 删掉末尾（已经在 k 处备份过了）
```

代价是**顺序被打乱了**。所以用之前必须问自己：这个数组的元素顺序有意义吗？如果无意义（比如一堆待处理的 ID），这就是免费的性能优化。

**技巧 2：批量删除用"覆盖计数"。**

如果要删掉数组中所有等于某个值的元素，不要每删一个就 pop 一次（那样最坏 O(n²)）。正确做法是维护一个写指针，把"要保留的元素"依次往前搬：

```python
def remove_all(arr, val):
    write = 0
    for read in range(len(arr)):
        if arr[read] != val:
            arr[write] = arr[read]
            write += 1
    return arr[:write]
```

一次遍历搞定 → **O(n)**。这就是 01 篇"只盯最内层循环"的实战应用：一个循环，线性时间。

### 六、Python 的 list 不是"纯数组"

Python 的 `list` 底层是**动态数组**——空间不够时会自动扩容（通常是扩大到原来的 1.125 倍左右），重新申请一块更大的连续内存并搬移全部元素。

所以 `append(x)` 在大多数时候是 O(1)，但**恰好触发扩容的那一次是 O(n)**。把扩容成本摊到所有 append 操作上，平均下来仍是 O(1)。

这种"偶尔很慢、平均很快"的复杂度，叫作**均摊时间复杂度**（amortized complexity）。这里先埋个伏笔，后面专题再展开。你现在只要记住：**不要因为某一次扩容慢，就认为 append 是 O(n)**。

### 七、这一篇你真正要带走的东西

1. **数组 = 连续内存**，这个物理特性决定了它的一切行为。
2. 连续 → **随机访问 O(1)**（直接算地址，无循环）。
3. 连续 → **插入删除 O(n)**（要搬移元素保持连续）。
4. "为什么从 0 开始"这类问题的通用答案：**把开销从高频路径上挪走**。
5. 面试技巧：不要求有序时用"末尾元素顶替"删除；批量删除用"覆盖计数"一次遍历。

下一篇我们看**链表**——它恰好和数组相反：随机访问 O(n)，插入删除 O(1)。理解了数组，链表就是顺理成章的对照。
