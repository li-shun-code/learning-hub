# 3. 提示词与上下文管理

给 AI 下指令，本质上和给一个「很聪明但完全不了解你项目、且不会主动猜你需要什么」的助手交代任务一样。指令越清楚，返工越少。

## 一、一个好指令的四个要素

| 要素 | 说明 | 例子 |
|---|---|---|
| **角色 / 背景** | 告诉 AI 它是谁、在什么场景下 | 「你是一个熟悉 Python 的后端工程师」 |
| **任务** | 具体要做什么，动词开头 | 「写一个用 FastAPI 实现的登录接口」 |
| **约束** | 技术栈、格式、边界、不做什么 | 「用 Pydantic 校验，密码不写日志，只返回 JSON」 |
| **验收标准** | 怎么算做完了 | 「写完后给出运行方式和两条 curl 测试命令」 |

把四要素合起来就是一个可直接用的指令：

```text
你是一个熟悉 Python 的后端工程师。
请写一个用 FastAPI 实现的登录接口 post /login：
- 接收 JSON：{"username": str, "password": str}
- 用 Pydantic 定义数据模型并做基本校验（用户名非空、密码长度至少 8）
- 不要把密码写进日志或返回给前端
- 成功返回 {"token": "..."}，失败返回 401
写完后，给出本地运行方式和两条 curl 测试命令。
```

## 二、迭代：一次不给全，分轮推进

复杂任务不要指望一条指令搞定。推荐节奏：

1. **第一轮**：给背景 + 任务 + 约束，拿到初稿；
2. **第二轮**：针对不满意的地方具体指出，例如「把密码校验改成必须包含大小写字母和数字」；
3. **第三轮**：让它解释关键代码、补测试、写文档。

每一轮都基于上一轮的结果，比一次性写一大段更有效。

## 三、上下文管理：AI 的「工作台」

「上下文」就是 AI 当前能看到的全部信息：你的指令、对话历史、它贴过的代码、你贴的文件。它有三个特点：

- **有限**：超过窗口长度，早期内容会被「挤出去」，AI 就忘了。
- **影响质量**：信息越多越杂，注意力越分散，回答越容易跑偏。
- **影响成本和速度**：上下文越长，每次响应越慢、越贵。

### 实用做法

- **一个任务一个会话**：别把写爬虫、写 FastAPI、问数学题混在同一个对话里。
- **及时开新会话**：话题切换时，直接新建会话，把必要的背景重新精简地给一遍。
- **给关键文件而非整个项目**：需要 AI 理解代码时，贴最相关的文件，而不是把所有文件都塞进去。
- **让 AI 自己总结**：长对话快结束时，说「请用 5 句话总结我们已完成的工作和当前状态」，把总结带到新会话里。

## 四、审查 AI 输出：必做的三件事

::: tip 审查三连
1. **跑一遍**：代码能不能运行？报错是什么？
2. **读一遍**：每一行的作用你能不能说清？说不清的让它解释。
3. **改一处**：故意改一个参数或条件，看结果是否符合预期——这是你真正理解它的证据。
:::

## 五、常见指令反面教材

| 反面例子 | 问题 | 改写方向 |
|---|---|---|
| 「帮我写个网站」 | 太模糊，无法执行 | 说明技术栈、页面、功能、数据 |
| 「这段代码不对，改一下」 | 没说哪里不对 | 指出具体现象和期望 |
| 「用最好的方法实现」 | 「最好」没有标准 | 给出明确的技术选型和约束 |
| 贴 500 行代码问「哪里错了」 | 上下文过载 | 先定位到出错函数，贴最小复现 |
